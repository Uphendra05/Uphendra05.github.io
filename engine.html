What is Ishtar Engine ?

View on GitHub →

Ishtar Engine is a Game Engine made using C++ and OpenGL, which can be used to create interactive applications, well technically video games. To put it straight Ishtar engine has capabilities of creating a game with some technical features a game has to offer. Below you can have full detailed review of what my engine can achieve and it is obviously not the extent my engine can achieve.

Off Screen Rendering

Rendering the scene to a Framebuffer and binding the Framebuffer to a Texture of the image inside imGUI to give us the result of rendering a screen on an editor. I'm using two different cameras to render two different scenes on two different textures. Each camera has its own framebuffer.

Frustrum Culling

Frustrum Culling is one of the major technical aspect in a video game. It steps in to optimize the scene by identifying what the camera view is seeing and culling all other objects that are not in the camera's view

Mesh Instancing

Mesh instancing is one of the graphics techniques implemented in Ishtar Engine to efficiently render repeated meshes.

Post Processing

Adding a secondary effect on top of the framebuffer which is currently bounded to a camera. You can Achieve these effects by creating a effect in shader for example Chromatic Aberration and binding the texture sampler 2D uniform to a quad and rendering the quad on top of the framebuffer.

LOD or Level Of Detail

Level Of Detail is a technical aspect every game uses nowadays. It is basically replacing number of meshes depending upon the distance of the game camera. The closer the game camera is the mesh with more vertices and polycount renders and the more far away from the object the mesh with least vertices and polycount renders. Sometimes we can even disable the model to save us from drawing every time in the scene.

Skeletal Animation

Skeletal Animation is a vast concept so I'm gonna try explaining it as brief as possible. First you load the 3D model as usual but while loading you make sure you generate bone hierarchy and store it to a bone node. This bone node is a struct that has all the information like transform and children data etcetera. Now you want to process the mesh meaning process all the vertices, indices and texture data. While doing that you have to extract the bone weight info for vertices.

Shadows

Shadows are the beauty of the game. For now my shadow is still work in progress and I've used the classic method of binding a depth buffer and drawing the scene from lights perspective and everything the light sees is not the shadow and everything the light can't see is the shadow.

Interior Mapping

Interior mapping creates the illusion of 3D rooms on flat surfaces by simulating a ray from the camera passing through a virtual cube behind the surface. In the shader, we calculate where this ray would hit the far side of the cube, then sample a cubemap using the direction from the cube’s center to that hit point. This gives each window a dynamic, perspective-correct view of an interior, without needing actual 3D geometry.

Deferred Rendering and Content Browser

Deferred rendering was implemented by splitting rendering into multiple passes: the geometry pass stores per-pixel data like positions, normals, albedo, and specular in the G-buffer; the lighting pass then uses this data to compute lighting in screen space via a full-screen quad. I'm using Uniform Buffer Objects (UBOs) to efficiently send light data to the shader, allowing support for a large number of dynamic lights.

PhysX Integration

The engine uses NVIDIA-PhysX as it’s physics engine. The engine provides an abstracted and easy to use Interface for the Physics object to work.
